# API Security Guard

סקיל לאודיט והקשחה של פרויקטים שקוראים ל-API של ספקי AI. מטרה אחת: **אפס חשיפה של מפתחות וסודות, ואפס דרך לנצל את ה-endpoints לרעה.**

עבוד לפי חמשת השלבים בסדר. אל תדלג. דווח למשתמש בעברית.

## עיקרון-על: עצירת חירום

אם בכל שלב נמצא מפתח חשוף (בקוד frontend, בהיסטוריית git, בקובץ שנגיש ציבורית, או בכל מקום שמישהו חיצוני יכול לקרוא) — **עצור מיד והודע למשתמש**. שום תיקון קוד לא מועיל כשהמפתח כבר בחוץ. המשתמש חייב לעשות rotation אצל הספק (platform.openai.com / console.anthropic.com) **לפני** שממשיכים. רק אחרי שהוא מאשר שסובב את המפתח — המשך לתיקונים.

## שלב 1 — סריקת חשיפות קיימות

זהה קודם את הסטאק (Node/Express, Next.js, PHP/WordPress, Python וכו') ואת מבנה הפרויקט — זה קובע איפה לחפש ואיך לתקן. קרא את `references/stack-notes.md` לפרטים ספציפיים לסטאק שזוהה.

1. **סריקת דפוסים** בכל הפרויקט (לא node_modules, כן dist/build/.next):
   ```bash
   grep -rEn --exclude-dir=node_modules --exclude-dir=.git \
     'sk-[a-zA-Z0-9_-]{20,}|sk-proj-|sk-ant-|AIza[a-zA-Z0-9_-]{30,}|API_KEY|SECRET|TOKEN|Bearer [a-zA-Z0-9]' \
     . | grep -vE '\.env\.example|placeholder|your-key-here'
   ```
   התאם את הדפוסים לספקים שבשימוש. חפש גם שמות משתנים חשודים שמוזרקים ל-frontend (למשל `VITE_`, `NEXT_PUBLIC_`, `REACT_APP_` עם ערכים סודיים — קידומות אלה נחשפות לדפדפן בכוונה!).

2. **בדיקת frontend ספציפית**: כל קובץ שנשלח לדפדפן (JS/TS/HTML בתיקיות public, dist, build, src של ה-client). מפתח שם = חשוף לכל העולם, גם אם "מוסתר" או מקודד base64.

3. **היסטוריית git**: `git log -p --all | grep -E 'sk-|API_KEY'` (או `git log -S "sk-" --all`). מפתח שהיה בקומיט בעבר נחשב שרוף גם אם נמחק — במיוחד אם הריפו ציבורי או היה ציבורי אי-פעם.

4. **קבצי תצורה**: `.env` (האם ב-.gitignore? האם בקומיט?), config.js/php, docker-compose.yml, קבצי CI/CD (.github/workflows), wp-config.php.

5. **דווח על כל ממצא לפני תיקון** — טבלה: קובץ, שורה, מה נמצא, רמת חומרה (חשוף ציבורית / חשוף פנימית / תקין).

## שלב 2 — ארכיטקטורה נכונה

6. וודא שכל קריאה לספק AI עוברת **אך ורק דרך ה-backend**. חפש בקוד ה-frontend קריאות ישירות ל-`api.openai.com`, `api.anthropic.com`, `generativelanguage.googleapis.com` וכו'.

7. אם קיימת קריאה ישירה מה-frontend — בנה endpoint proxy בצד השרת: מקבל את הבקשה מהלקוח, מאמת, בונה את הקריאה לספק בעצמו עם המפתח מ-env. תבנית מוכנה ב-`references/proxy-templates.md`.

8. כל הסודות נטענים מ-`process.env` (או מקבילה בסטאק) בלבד. אפס ערכים hardcoded, גם לא "זמנית".

9. וודא ש-`.env` ב-.gitignore, וצור `.env.example` עם placeholders בלבד (`OPENAI_API_KEY=your-key-here`).

## שלב 3 — הגנה על ה-endpoints

הרעיון: גם עם מפתח מוגן בשרת, endpoint פתוח הופך את השרת שלך למפתח ציבורי בפועל. כל בקשה שמגיעה ל-LLM עולה כסף, ולכן:

10. **אימות**: כל endpoint שמפעיל AI חייב אימות משתמש (session/JWT/API key פנימי). אסור endpoint אנונימי שמגיע ל-LLM. אם המוצר דורש שימוש אנונימי (למשל צ'אט לפני הרשמה) — הגבל אגרסיבית לפי IP + fingerprint והוסף CAPTCHA אחרי N בקשות.

11. **Rate limiting** per-user ו-per-IP על כל נתיב שקורא ל-AI. ברירת מחדל סבירה: 10 בקשות/דקה למשתמש, 30/דקה ל-IP, עם חסימה זמנית מדורגת. השתמש בספרייה קיימת של הסטאק (express-rate-limit, next-rate-limit וכו').

12. **פרמטרים נשלטים בשרת בלבד**: הלקוח לא קובע model, max_tokens, system prompt או temperature. כל אלה hardcoded בצד השרת. פרמטר שמגיע מהלקוח ומועבר as-is לספק = פרצה (מישהו ישלח max_tokens=100000 ו-model=הכי יקר).

13. **Validation על הקלט**: הגבלת אורך (למשל 2,000 תווים), סינון קלט ריק, ודחיית payload חריג לפני שהבקשה בכלל נוגעת בספק.

14. **CORS מצומצם**: רק הדומיינים של האתר עצמו. לא `*`.

## שלב 4 — ניטור ובקרה

15. **לוג לכל קריאת AI**: user_id, IP, timestamp, endpoint, tokens used (מה-response של הספק), עלות משוערת. בלי זה אי אפשר לאתר ניצול בדיעבד.

16. **תקרות שימוש**: תקרה יומית per-user ותקרה גלובלית יומית. חצייה → החזר 429 בלי לקרוא לספק. זו רשת הביטחון שהופכת "חשבון של $4,000" ל"חשבון של $40".

17. המלץ למשתמש להגדיר גם **hard limit חודשי בדשבורד של הספק** — הגנה אחרונה שעובדת גם אם כל הקוד נכשל.

## שלב 5 — דוח סיכום

הצג טבלה בעברית:

| # | ממצא | חומרה | סטטוס | פעולה ידנית נדרשת |
|---|------|--------|--------|---------------------|

חלוקה לשלוש קטגוריות: **תוקן אוטומטית**, **דורש אישור לתיקון**, **דורש פעולה ידנית של המשתמש** (rotation, הגדרת env בפרודקשן, הגדרת limits בדשבורד הספק).

סיים עם צ'קליסט "לפני עלייה לאוויר" קצר שהמשתמש יכול לוודא בעצמו.

## הערות חשובות

- **אל תדפיס מפתחות שנמצאו** בדוח או בצ'אט — הצג רק 6 תווים ראשונים + מיקום (`sk-pro...` בקובץ X שורה Y).
- אם הפרויקט רץ על AppDeploy — הסודות מנוהלים דרך secrets של הפלטפורמה, לא קבצי .env; וודא שהקוד משתמש במנגנון הזה.
- אם זו מערכת WordPress — המפתחות שייכים ל-wp-config.php או ל-options מוצפנים, לעולם לא בקוד של theme/plugin שנגיש ב-wp-content.
- ההסבר למשתמש תמיד בעברית, הקוד והקומיטים באנגלית.
